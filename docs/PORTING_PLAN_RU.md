# Redragon K530RGB: анализ установщика и план переноса на macOS

Дата: 21 октября 2026 года.

## Вывод

Нативный аналог для Mac с Intel и Apple Silicon выглядит технически осуществимым. Рекомендуемый путь — восстановить протокол управления штатной прошивкой и реализовать новое приложение на Swift/SwiftUI с HID-транспортом через IOKit. Перенос самого InstallShield-установщика не решает задачу: внутри находится Windows-приложение, которому нужна замена Windows API и интерфейса.

Это предварительная оценка осуществимости, а не подтверждённая совместимость. Клавиатура в ходе исследования не опрашивалась, команды на неё не отправлялись. Критический следующий результат — успешная проверка интерфейса управления и одной команды на реальном устройстве.

## 1. Что исследовано

Исходный файл: `Rdragon K530RGB Keyboard - Port.exe`.

- Размер: 13 275 502 байта.
- SHA-256: `de4b11b71805fc0ea76452a7c9fbe74b67a044e3a67caa538b548a3041f4c573`.
- Тип: PE32, Windows GUI, Intel i386.
- Упаковка: InstallShield; `setup.ini` сообщает `EngineVersion=15.0.0.591`.
- Название продукта внутри: `Redragon K530RGB Mechanical Keyboard`.
- Извлечены `data1.cab`, `data1.hdr`, `data2.cab`, `setup.ini`, затем все 127 файлов кабинетов.
- Отдельная проверка содержимого средствами unshield завершилась успешно для 127 файлов. Она проверяет целостность извлечения, а не безопасность или происхождение программы.

EXE и DLL не исполнялись. Выполнены распаковка, анализ PE-заголовков, импортов, экспортов, строк, конфигураций и отдельных участков дизассемблирования. Содержимое файлов рассматривалось как данные, а не как инструкции к действиям.

### Подтверждённые находки

| Компонент | Результат анализа | Значение для порта |
|---|---|---|
| Основное приложение | `Redragon K530RGB Keyboard.exe`, 4 007 936 байт, PE32 i386 | Нужна новая macOS-программа |
| Технология интерфейса | Многочисленные классы MFC, Win32, GDI/GDI+ | Интерфейс следует реализовать заново |
| .NET | CLR Runtime Header равен нулю у основной программы и HidServ.dll | Это не .NET-приложение; наличие служебного dotnetinstaller.exe не меняет вывод |
| Связь с устройством | `HidServ.dll`, 36 352 байта, PE32 i386 | Windows-библиотека требует замены |
| Импорты HidServ.dll | `HidD_GetFeature`, `HidD_SetFeature`, `HidP_GetCaps`, `SetupDi*`, `ReadFile`, `WriteFile` | Используется стандартная инфраструктура HID Windows |
| Экспорты HidServ.dll | `Init`, `RequestGetDeviceCount`, `RequestGetFeature`, `RequestSetFeature`, `RequestStatusSetFeature`, `RequestWrite`, другие | Есть удобные точки для восстановления операций протокола |
| Загрузка DLL | Основная программа загружает HidServ.dll и получает адреса функций динамически | Прямые вызовы нужно отслеживать через таблицу указателей |
| Драйверы | В 127 извлечённых файлах нет `.sys` или `.inf`; в DIFxData.ini поддержка всех перечисленных архитектур отключена | Отдельный драйвер Windows в этом пакете не обнаружен |
| Ресурсы | INI, JPG/BMP/PNG, `.userd`, бинарный `peizhi.ini` | Можно изучать раскладку, строки интерфейса и форматы настроек |
| RAR внутри | Содержит `.ai` и `.jpg` макета интерфейса | Это дизайнерские материалы, не исходный код |

PE-метки времени: основное приложение — 17 октября 2019 года, HidServ.dll — 1 декабря 2013 года. Эти поля не доказывают дату выпуска. У основного приложения и HidServ.dll таблица Security Directory пуста: встроенная подпись Authenticode в них не обнаружена. Проверка на вредоносность в задачу не входила.

### Предварительные HID-идентификаторы

В основной программе по виртуальным адресам `0x65505C`, `0x655074`, `0x65508C` найдены похожие структуры с байтами `45 0C 04 50`. При интерпретации как двух little-endian 16-битных полей это соответствует VID `0x0C45`, PID `0x5004`.

Следующие пары полей похожи на Usage Page / Usage:

| Кандидат | Usage Page | Usage |
|---|---|---|
| Структура 1 | `0xFFFF` | `0x0001` |
| Структура 2 | `0x000C` | `0x0001` |
| Структура 3 | `0xFF1C` | `0x0092` |

Это интерпретация статических данных, которую следует проверить по логике HidServ.dll и дескрипторам устройства. Не использовать эти значения как достаточное основание для отправки команд. Одинакового VID/PID может быть недостаточно для отличения аппаратных ревизий.

### Обнаруженная поверхность функций

Ресурсы описывают три профиля, подсветку и её яркость/скорость, индивидуальные цвета, переназначение клавиш, мультимедийные действия, редактор макросов и Magic FN. В `Main.ini` перечислено 19 названий режимов подсветки: номера 1–18 и 20. Есть четыре файла `UserDengColor_*.userd`.

Наличие строки или элемента интерфейса не доказывает поддержку функции конкретной прошивкой. Строки обновления прошивки и резервного копирования также есть, но работоспособный механизм обновления этим не подтверждён. Файлы прошивки с расширениями `.bin`/`.hex` среди извлечённых файлов не найдены; это не исключает встроенных бинарных данных.

## 2. Варианты решения

| Вариант | Оценка |
|---|---|
| SwiftUI + IOKit HID | Предпочтительный путь для macOS: нативный интерфейс и небольшое число зависимостей |
| Qt/C++ + HIDAPI | Разумная альтернатива, если планируется поддержка Windows/Linux из общего проекта |
| Wine/CrossOver | Только отдельный эксперимент: запуск интерфейса не доказывает работоспособность доступа к нужным HID-интерфейсам |
| Windows в виртуальной машине | Возможный стенд для записи USB-трафика при рабочем USB passthrough; это не нативный порт |
| OpenRGB | Источник для сравнения протокола EVision и отдельная проверка части RGB-функций; полная совместимость K530 и перенос макросов не установлены |
| SonixQMK/VIA | Отдельная замена прошивки, а не перенос штатной программы; требует точного определения платы и проверки сохранения Bluetooth и восстановления |

Rosetta не преобразует Windows PE и Win32/HID API в macOS-приложение. Даже Intel Mac требует адаптации к macOS. Для нового приложения достаточно общего исходного кода с двумя нативными архитектурами: `x86_64` и `arm64`.

## 3. Предлагаемая архитектура

```text
SwiftUI / AppKit — окно клавиатуры, подсветка, профили, макросы
                         ↓
Сервисы настроек — проверка значений, очередь операций, сохранение
                         ↓
K530Protocol — кодирование команд и разбор ответов
                         ↓
HIDTransport — IOHIDManager / IOHIDDevice
                         ↓
Штатная прошивка K530 через USB
```

Модули будущего проекта:

- `DeviceDiscovery`: перечисление устройств, фильтр VID/PID и Usage, определение поддерживаемой ревизии, подключение/отключение.
- `HIDTransport`: открытие нужного интерфейса без захвата основного ввода, Feature/Output Reports, таймауты, обработка ошибок.
- `K530Protocol`: чистые функции сериализации, report ID, длины, порядок байтов, контрольные суммы и последовательности команд.
- `DeviceSession`: последовательное выполнение команд, отмена при отключении, проверка подтверждений. Повтор записи — только если известна безопасность повторного выполнения.
- `Profiles`: локальный версионируемый формат JSON; импорт старых форматов после их изучения.
- `UI`: визуальная раскладка, эффекты, переназначения, редактор макросов, понятные статусы ошибок.

Обмен с HID не выполнять на главном потоке. В частности, IOHIDDeviceSetReport — синхронный вызов. Для протокола использовать явные целочисленные размеры, не переносить 32-битные Windows-структуры или указатели побайтно в Swift.

Начинать с пользовательского HID API. Не закладывать kernel extension или DriverKit без доказанной необходимости. Наличие стандартных HID-вызовов делает этот путь перспективным, но права доступа и возможность открытия нужной коллекции проверяются экспериментально.

## 4. План реализации и критерии готовности

### Этап 1. Инвентаризация реального устройства — ориентир 1–2 рабочих дня

1. Подключить K530 по USB-кабелю с передачей данных.
2. Записать VID/PID, версии устройства, интерфейсы, Usage Page/Usage, report descriptor, размеры Feature/Input/Output Reports и report ID.
3. Сопоставить с найденными статическими структурами; отличить K530 от K530 Pro и других ревизий.
4. Проверить перечисление и открытие служебного интерфейса на Intel и Apple Silicon.

Критерий: устройство однозначно определяется; его открытие не мешает обычному вводу; сохранён диагностический отчёт.

### Этап 2. Восстановление протокола — ориентир 3–7 рабочих дней

1. Проследить обращения приложения к функциям HidServ.dll, определить буферы и ветви обработки ответов.
2. На Windows-стенде записать USBPcap/Wireshark-трафик штатной программы: запуск, чтение настроек, изменение одного параметра, применение, повторное чтение.
3. Менять по одному параметру: режим, цвет, яркость, затем одна клавиша и короткий макрос.
4. Описать заголовки, report ID, длины, команды, адреса/смещения, checksum, подтверждения и задержки.
5. Отделить чтение, временное применение, сохранение во flash и команды загрузчика.
6. Сравнить RGB-часть с открытым кодом контроллеров EVision, если совпадают устройство и формат обмена.

Критерий: спецификация с эталонными пакетами и ответами; подтверждено безопасное чтение и одно изменение с возможностью восстановления исходной настройки. Не воспроизводить неизвестные пакеты вслепую.

Это контрольная точка проекта. Если служебная коллекция недоступна или протокол отличается, архитектуру и сроки пересмотреть до разработки полноценного интерфейса.

### Этап 3. Диагностическая утилита macOS — ориентир 2–4 рабочих дня

Создать небольшую CLI-утилиту на Swift: список подходящих устройств, экспорт дескрипторов, чтение подтверждённых параметров, диагностический журнал. Режим записи добавить после проверки протокола и ограничить известными командами.

Критерий: результаты чтения совпадают со штатной программой; подтверждённая команда работает на обеих архитектурах, после переподключения и при обработке ошибок.

### Этап 4. Минимальное приложение — ориентир 4–7 рабочих дней

Реализовать обнаружение устройства, состояние подключения, выбор режима/цвета/яркости из подтверждённых возможностей, явную кнопку применения, локальное сохранение профиля и ошибки связи.

Критерий: пользователь меняет подсветку без Windows, может вернуть исходную настройку; обычный ввод сохраняется; приложение выдерживает отключение кабеля и выход Mac из сна.

### Этап 5. Расширенные функции — ориентир 5–10 рабочих дней

Добавить аппаратные переназначения, макросы, Magic FN, профили и импорт/экспорт по мере подтверждения протокола. Проверять ограничения памяти и длительности макросов, не брать их из общих строк интерфейса.

Внутренний формат клавиш строить на USB HID usages. Значения `KEY_001`, `KEY_002` и подобные из старых INI похожи на Windows scan codes: необходима явная таблица преобразований. Отдельно проверить Command/Option/Control, раскладки и Windows-сочетания вроде Ctrl+C: их буквальный перенос не обеспечивает привычное поведение macOS.

Если макрос хранится в клавиатуре, приоритет — аппаратное исполнение. Программное воспроизведение и глобальная запись событий на Mac — отдельная функция с проверкой необходимых разрешений Accessibility/Input Monitoring. Для простой отправки RGB-команд эти разрешения заранее не требовать.

Критерий: для каждой функции есть проверка запись → чтение, сравнение со штатной программой и проверка поведения после отключения приложения/питания.

### Этап 6. Совместимость и распространение — ориентир 3–5 рабочих дней

1. Собрать Universal 2 с `x86_64` и `arm64`, включая все библиотеки и вспомогательные программы.
2. Предварительно рассмотреть macOS 13+ как нижнюю границу; окончательно выбрать после уточнения моделей MacBook, доступного SDK и проверки сборок обеих архитектур.
3. Проверить физический Intel MacBook и физический MacBook Apple Silicon. Запуск x86_64 через Rosetta на ARM не заменяет проверку Intel-оборудования.
4. Проверить прямой USB, USB-C переходник/хаб, переподключение, сон, несколько HID-устройств и несколько K530, отсутствие устройства и отказы доступа.
5. Подготовить `.app` в `.dmg`, Developer ID signing, Hardened Runtime, notarization и проверку на чистом Mac.
6. До распространения отдельно определить допустимость включения фирменных изображений и бинарников; для самостоятельного аналога предпочтителен собственный интерфейс.

Критерий: один установочный образ запускается нативно на обеих архитектурах и проходит согласованную матрицу функций/версий macOS.

Суммарный предварительный ориентир: 18–35 рабочих дней одного разработчика на основной путь без отдельного резерва. Плановый бюджет с запасом — примерно 4–8 рабочих недель. Это экспертная оценка, не измеренный срок; неизвестный протокол, аппаратные ревизии и доступность стендов могут увеличить её. MVP подсветки можно выделить отдельно после этапов 1–3.

## 5. Что потребуется для следующего этапа

- Конкретная K530, её точная маркировка/ревизия и USB-кабель с передачей данных.
- Intel MacBook и MacBook Apple Silicon; версии macOS, которые нужно поддерживать.
- Рабочий Windows-стенд для штатной программы и USB-захвата. На виртуальном стенде сначала проверить захват составного HID-устройства целиком.
- Xcode/Swift с поддержкой выбранных macOS и обеих архитектур.
- USBPcap/Wireshark и инструмент статического анализа, например Ghidra, для дальнейшего исследования.
- Для публичного распространения — инфраструктура подписи и notarization Apple.

Bluetooth вынести в отдельное исследование. Работа обычного ввода по Bluetooth не доказывает наличие канала конфигурации. Сначала выяснить, сохраняются ли USB-настройки и действуют ли они в беспроводном режиме; только затем исследовать самостоятельное управление по Bluetooth.

Обновление прошивки исключить из первой версии. Оно требует отдельного подтверждённого протокола, точного определения ревизии, проверки образов и рабочего восстановления. Статический анализ установщика не даёт этих гарантий.

## 6. Материалы исследования

Перечисленные ниже пути описывают полный локальный снимок. В публичный репозиторий включены документы, манифест, журналы и кандидаты HID-структур. Исходный установщик доступен в `installers/Rdragon K530RGB Keyboard - Port.exe`. Кабинеты, распакованные бинарники, полные PE-отчёты и дизассемблирование остаются на исходном компьютере в ZIP-снимке; его нужно перенести отдельно. См. HANDOFF_RU.md.

- `analysis/manifest.json`: размеры и SHA-256 всех 127 извлечённых файлов.
- `analysis/installer/`: кабинеты и setup.ini.
- `analysis/extracted/`: извлечённые файлы приложения и установщика.
- `analysis/extraction.log`, `analysis/integrity.log`: результаты распаковки и проверки.
- `analysis/application-pe.txt`, `analysis/hidserv-pe.txt`: заголовки PE, импорты и экспорты.
- `analysis/application-disassembly.txt`, `analysis/hidserv-disassembly.txt`: дизассемблирование для последующей работы.
- `analysis/hid-descriptor-candidates.json`: точные байты кандидатов HID-структур.

Эти материалы не являются готовым приложением; инструкции по запуску macOS-порта появятся после его реализации. Исходный установщик сохранён без изменений.

## Источники по платформе и инструментам

- [unshield](https://github.com/twogood/unshield) — инструмент распаковки InstallShield, использованный при анализе.
- [SonixQMK](https://sonixqmk.github.io/SonixDocs/) — отдельный путь работы с прошивками Sonix/EVision; соответствие конкретной платы требует проверки.

Находки о содержимом установщика получены локально. Документация Apple подтверждает возможности платформы, но не совместимость конкретной клавиатуры.
