# Автоматические обновления K530 Lighting

## Доступ к релизам

Репозиторий приватный. `AppUpdater` обращается к GitHub API и assets через URLSession без авторизации: текущая реализация не получает приватные релизы. Установка такого обновления выполняется вручную через страницу Releases под аккаунтом с доступом. Ответ 404 не означает отсутствие нового приватного релиза.

Подпись Ed25519 подтверждает подлинность архива, но не заменяет доступ к GitHub. Встраивать токен владельца в `.app` нельзя. Для автоматической доставки потребуется отдельно настроенный канал, доступный клиенту, или пользовательская авторизация; текущий код этого не реализует. Изменение видимости репозитория — отдельное решение владельца.

## Поведение

`AppUpdater` проверяет последний стабильный GitHub Release через 30 секунд после запуска и затем каждые 6 часов. Сеть работает в фоне. Фоновая проверка не показывает модальное окно и не перехватывает фокус: новый тег (например, `v0.4.0`) отображается в строке состояния панели, а в меню значка пункт «Проверить обновления…» сменяется на «Установить версию…». Диалог «Скачать» / «Позже» показывает только ручная проверка. Настройки клавиатуры при этом не меняются.

После согласия: проверка подписи описания → загрузка с процентами (если сервер сообщает размер) → SHA-256 → распаковка → проверка bundle и подписи кода → установка → запуск новой версии и завершение старой. Для этапов без известного процента UI показывает неопределённый индикатор и текст операции. Повторные проверки во время загрузки исключены.

Для отсутствующего ключа показывается объяснение и открывается страница релиза для ручной установки. Неподписанные обновления автоматически не устанавливаются. Нет повышения привилегий: папка приложения должна быть доступна пользователю для записи. Из App Translocation установить нельзя; сначала нужно переместить приложение в «Программы».

## Архитектура

`tools/k530menu/Sources/AppUpdater.swift` использует Foundation URLSession, Combine, AppKit и CryptoKit (системные библиотеки). Интерфейс наблюдает `message`, `progress: Double?`, `isBusy`; вызывает `start()` один раз и `checkManually()` по команде меню. SHA-256 архива включён в описание, подписанное Ed25519. Публичный ключ хранится в ресурсах установленной доверенной сборки; секретный ключ нужен только машине выпуска.

Система установки не меняет прошивку и не удаляет локальные профили в Application Support. Обычный выход блокируется во время загрузки/установки; после успешной замены разрешается намеренное завершение для перезапуска. Старый bundle сохраняется рядом в скрытой папке `.K530Lighting-backup-UUID.app`. При ошибке перемещения или команды запуска восстанавливается старый bundle; откат выполняется только переименованиями внутри одной папки. Успешная команда `/usr/bin/open -n` подтверждает принятие запроса запуска системой, но не гарантирует отсутствие последующего сбоя новой версии; при таком сбое резервную `.app` можно запустить вручную. Когда новая версия проработает 30 секунд, она сама удаляет скрытые `.K530Lighting-backup-UUID.app` и незавершённые `.K530Lighting-update-UUID.app` в своей папке.

## Упаковка текущего выпуска 0.4.0

Из корня проекта:

```sh
./tools/k530menu/package.sh
```

Скрипт вызывает универсальную сборку, проверяет подпись bundle, создаёт `dist/K530Lighting-0.4.0-macOS-universal.dmg` с приложением и ссылкой на Applications, ZIP для обновления, `SHA256SUMS`, `update.json` и `update.json.sig`. Подпись описания проверяется публичным ключом из собранного приложения. При отсутствии ключа или несовпадении пары выпуск отменяется; существующие итоговые артефакты не заменяются неподписанными файлами.

Закрытый ключ по умолчанию берётся из связки ключей входа (служба `dev.slipcast.k530.update-signing`). Переменная `K530_UPDATE_PRIVATE_KEY` задаёт файл ключа или значение `keychain`. Прежний файл `~/Library/Application Support/K530Lighting/ReleaseKeys/update-signing.key` ещё поддерживается, но скрипт предупреждает о нём. `SWIFT_MODULECACHE_PATH` задаёт кэш модулей Swift. Секретный ключ в архивы не включается. `dist/` и `.build/` не входят в Git.

Это локальная упаковка, а не публикация: URL в манифесте начнёт работать только после размещения файлов в стабильном GitHub Release `v0.4.0`. Для автообновления необходим ZIP, DMG нужен для ручной установки.

## Подготовка подписанных выпусков

1. Один раз создать ключи на машине выпуска, указав путь закрытого ключа вне репозитория:

   ```sh
   swiftc -module-cache-path /tmp/k530-sign-cache -framework CryptoKit tools/k530menu/Updates/SignUpdate.swift -o /tmp/k530-sign-update
   /tmp/k530-sign-update keygen /защищённый/путь/k530-update.key tools/k530menu/UpdatePublicKey.txt
   ```

2. Сохранить закрытый файл (права `0600`) в защищённом хранилище и резервной копии. Не публиковать и не коммитить его. Публичный `UpdatePublicKey.txt` включить в исходники доверенной сборки и скопировать в `Contents/Resources/UpdatePublicKey.txt`. Потеря закрытого ключа потребует ручного распространения новой доверенной сборки.
3. Собрать приложение с увеличенными `CFBundleShortVersionString` и числовым `CFBundleVersion`. Версия описания должна совпадать с тегом GitHub без `v`, номер сборки — строго возрастать. Упаковать `K530Lighting.app` в корне ZIP:

   ```sh
   ditto -c -k --sequesterRsrc --keepParent tools/k530menu/.build/K530Lighting.app K530Lighting-0.4.0-macOS-universal.zip
   shasum -a 256 K530Lighting-0.4.0-macOS-universal.zip
   ```

4. Создать `update.json` с реальной SHA-256 и адресом архива будущего релиза:

   ```json
   {
     "version": "0.4.0",
     "build": 7,
     "archive": "https://github.com/Slipcast-dev/Rdragon-K530RGB-Keyboard-Port/releases/download/v0.4.0/K530Lighting-0.4.0-macOS-universal.zip",
     "sha256": "ЗАМЕНИТЬ_НА_64_ШЕСТНАДЦАТЕРИЧНЫХ_СИМВОЛА",
     "minimumSystemVersion": "11.0"
   }
   ```

5. Подписать точные байты JSON. После подписи JSON не редактировать:

   ```sh
   /tmp/k530-sign-update sign /защищённый/путь/k530-update.key update.json update.json.sig
   ```

6. Прикрепить ZIP, `update.json` и `update.json.sig` к одному стабильному GitHub Release. Сам публичный ключ в релизе не является источником доверия: клиент использует только ключ из установленного приложения.

Архив должен содержать universal-приложение для обеих архитектур; модуль не выбирает отдельные arm64/x86_64 assets. Предельный размер загрузки — 250 МБ. Действующая подпись приложения проверяется `codesign --verify --deep --strict`; ad-hoc допустима, поскольку происхождение всего архива проверяет отдельная доверенная Ed25519-подпись. Обновление ad-hoc-приложения может потребовать повторно выдать «Мониторинг ввода» в macOS. Для стабильной идентичности разрешений нужен Developer ID и notarization.

## Проверки

```sh
swiftc -module-cache-path /tmp/k530-tests-cache -framework CryptoKit tools/k530menu/Sources/AppLocalization.swift tools/k530menu/Sources/AppUpdater.swift tools/k530menu/Tests/UpdaterTests.swift -o /tmp/k530-updater-tests
/tmp/k530-updater-tests
```

Тест проверяет правильную подпись, подмену байтов, чужой ключ, запрещённые URL, откат номера сборки, формат SHA-256, несовместимую macOS, несколько доверенных ключей, откат замены каталога `.app` и очистку резервных копий. До публикации требуется отдельная проверка полного цикла на двух локальных подписанных тестовых выпусках: «Позже», загрузка, обрыв сети, повреждённый ZIP, недоступная папка, успешная замена, перезапуск и повторное разрешение ввода. Эти интеграционные сценарии автоматически не выполняют замену рабочего приложения пользователя.

Основы проверки подписи: [Apple CryptoKit](https://developer.apple.com/documentation/cryptokit/curve25519/signing/publickey/isvalidsignature(_:for:)). Рекомендации по доверенным подписям обновлений: [Sparkle documentation](https://sparkle-project.org/documentation/).

## Хранение ключей выпуска

Публичный ключ уже создан в `tools/k530menu/UpdatePublicKey.txt` и включается скриптом сборки автоматически. Повторно выполнять `keygen` для существующей линии обновлений не нужно.

Утечка закрытого ключа позволяет установить любой код всем пользователям автообновления, поэтому обычный файл на диске — временное решение. Перенос в связку ключей (элемент доступен только на этом Mac после разблокировки и не синхронизируется):

```sh
swiftc -framework CryptoKit -framework Security tools/k530menu/Updates/SignUpdate.swift -o /tmp/k530-sign-update
/tmp/k530-sign-update keychain-import "$HOME/Library/Application Support/K530Lighting/ReleaseKeys/update-signing.key"
/tmp/k530-sign-update public keychain   # должен совпасть с UpdatePublicKey.txt
```

После проверки сохраните зашифрованную офлайн-копию ключа и удалите файл (`rm -P`). При подписи macOS спросит разрешение на доступ к элементу связки.

### Смена ключа

`UpdatePublicKey.txt` может содержать несколько ключей — по одному base64 в строке, строки с `#` пропускаются. Приложение принимает подпись любым из них. Порядок смены:

1. Создать новый ключ (`keygen` во временные файлы, затем `keychain-import` под другой службой или на другой машине) и добавить его публичную часть второй строкой.
2. Выпустить версию с обоими ключами, подписанную **старым** ключом: её примут все установленные копии.
3. Следующие выпуски подписывать новым ключом. Когда старые копии обновятся, удалить старый ключ из файла.

При компрометации ключа выпуск без него, подписанный новым ключом, отзывает его только у обновившихся пользователей; остальным нужна ручная установка. Поэтому скомпрометированный ключ нужно убирать из файла как можно раньше.
